# Мультиарендность (отдельная БД на колледж)

## Архитектура
- **Одна БД на колледж (tenant).** Реестр колледжей и супер-админы — в отдельной
  **control-БД** `psych_control`.
- На каждый колледж — свой пул соединений (`tenantPool(dbName)` в `server.js`).
- Имя новой БД строится из безопасного `TENANT_DB_PREFIX` (по умолчанию `psych_t_`)
  и кода колледжа.
- Колледж определяется **кодом на входе**: поле `college` в `/api/auth/login`.
  Пусто → колледж по умолчанию (`default` → существующая `psych_diagnostic`),
  поэтому старый вход не ломается. Код колледжа зашит в JWT (`tenantDb`), и
  `authenticateToken` подставляет `req.db = tenantPool(...)`. Все маршруты ходят в `req.db`.
- Супер-админ (владелец SaaS) входит с кодом колледжа **`platform`**
  (таблица `platform_admins`).

## Подготовка БД на сервере (один раз)
1. Дать пользователю приложения право создавать БД (под root MySQL):
   ```sql
   GRANT ALL PRIVILEGES ON *.* TO 'psyagent_user'@'localhost' WITH GRANT OPTION;
   FLUSH PRIVILEGES;
   ```
2. Запустить приложение (`npm install`, затем перезапуск). При старте сервер сам создаст
   `psych_control`, «default»-колледж (→ `psych_diagnostic`) и первого супер-админа
   из обязательных production-переменных `SUPERADMIN_USER` / `SUPERADMIN_PASSWORD`.

## Что ПРОВЕРИТЬ на реальной БД (критично — изоляция данных)
> Эти проверки нужно выполнять **на сервере**, где есть доступ к MySQL
> (`mysql -u root -p ...` или через `psyagent_user`). Отсюда (dev-машина) БД не видно.
1. Логи старта содержат `Control-БД готова` и строку про супер-админа.
2. Обычный вход (без кода колледжа) и супер-админ (код `platform`) работают.
3. `SELECT * FROM psych_control.tenants;` — есть строка `default`.
4. **Изоляция:** создать второй колледж (см. фазу 2), завести в нём студента, и
   убедиться, что под админом первого колледжа его НЕ видно (и наоборот). Это
   главный риск рефактора — что какой-то запрос остался на чужом пуле.
